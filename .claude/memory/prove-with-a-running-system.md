ทุกครั้งที่ตัดสินใจอะไรใน PTL ผู้ใช้คาดหวังให้ **รันของจริงพิสูจน์** แล้วเอาตัวเลขจริงกลับมาใส่เอกสาร ไม่ใช่แค่บรรยายว่าออกแบบไว้ยังไง

**Why**: ทุกครั้งที่ลงมือรันจริง **เจอบั๊กที่การอ่านโค้ดไม่เจอ** — เช่น forwarder กันลำดับด้วย `id` แล้วชนกับ `seq` เอง (เลนค้างถาวร) · WMS ตอบ 500 ตอน `box_closed` มาหลัง batch จบ · vendor ไม่เคยเช็ค `version` เลยทั้งที่สเปกบังคับ · `"batches": null` ทำให้คิวรี sweep ระเบิดเงียบ ๆ · form ซ้อน form ทำให้ปุ่มในตารางกดไม่ติด (curl จับไม่ได้ ต้องใช้เบราว์เซอร์จริง)

**How to apply**:
- แก้เสร็จแล้วรัน `docker compose down -v && up --build` แล้วเดินครบวงบน volume ใหม่เสมอ · เทียบตัวเลข: batch จบ / กล่อง+SO / inbound ค้าง / matched-ignored / alert
- **จงใจทำให้พัง** เพื่อพิสูจน์ว่า alert ยิงจริงและ**ปิดเองเมื่อเรื่องจบ** ไม่ใช่แค่มีโค้ดเขียนไว้
- เรื่อง UI ต้องตรวจด้วยเบราว์เซอร์จริง (`simchrome:1` + `--dump-dom`) — `curl` มองไม่เห็นพฤติกรรม parser · มีสคริปต์ `app/tools/check_forms.py` ไว้แล้ว
- เอาตัวเลขที่วัดได้ไปตั้งค่า config จริง เช่น `gapWait = 10s` มาจาก p95 ของเวลาในสายส่ง 0.95 วิ
- เจอบั๊กระหว่างทางให้**รายงานตรง ๆ** และบันทึกไว้ในช่อง gap ด้วย ผู้ใช้ให้ค่ากับการเจอบั๊กมากกว่าการรายงานว่าผ่านหมด
