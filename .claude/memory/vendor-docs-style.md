ผู้ใช้ตรวจสเปกฉบับส่ง vendor แล้วสั่งแก้ยกชุด (2026-09-21) — กติกาที่ตกผลึกและต้องใช้กับเอกสารส่งออกทุกฉบับต่อจากนี้

**Why**: เอกสารเดิมอ่านได้เฉพาะคนที่อยู่ในโปรเจกต์มาตั้งแต่ต้น — เต็มไปด้วยเลข gap (`G60`), ป้าย `[แก้ 2026-09-16]`, ข้อความขีดฆ่าของที่เลิกใช้, และศัพท์ "ขาขึ้น/ขาลง" ที่ vendor ต้องแปลในหัวว่าขาไหนคือใคร

**How to apply**

| ห้ามมี | ใช้แทน |
|---|---|
| เลข gap (`G56` · `G42/G51`) | ไม่ต้องอ้างเลย — เหตุผลอยู่ใน gap log ฝั่งเรา |
| ป้ายรายบรรทัด `[ใหม่ ...]` `[แก้ 2026-09-16]` `[ตัดสิน ...]` | **แสดงเวอร์ชันที่เดียว** บนหัวเอกสาร + ตารางประวัติเวอร์ชันท้ายเอกสาร |
| ข้อความขีดฆ่า `~~ของเก่า~~` + ตาราง "v3 เปลี่ยนเป็น v4 ตรงไหน" | ตัดทิ้ง — vendor ไม่เคยเห็นของเก่า |
| "ขาขึ้น / ขาลง / ด่าน 1" | **เรียกจากมุมผู้อ่าน**: "ข้อความที่คุณส่ง" / "ข้อความที่คุณรับ" · ชื่อ component เรียกตามหน้าที่ (publisher / consumer / forwarder) |
| รายการอ้างอิงไฟล์ภายใน | ตัด — vendor เปิดไม่ได้อยู่แล้ว |

**เขียนเวอร์ชันสัญญาให้เริ่มที่ `1.0`** ตอนยังไม่เคยส่งให้ vendor — ไม่ต้องลากประวัติ v4.1 ที่เป็นเลขภายในของเรามา และกำกับไว้ในเอกสารว่า "ในเนื้อเอกสารจะไม่มีป้ายรายบรรทัด ให้ยึดฉบับล่าสุดเป็นความจริง"

**field ที่คนสับสนให้แยกเป็นหัวข้อของตัวเอง** พร้อมตาราง + ตัวอย่างเดินตัวเลขจริง ไม่ใช่ยัดเป็นแถวในตารางรวม — ทำแบบนี้กับ `version` (2.2), ตระกูล `qty` (2.3) และ routing key (`ptl-rabbitmq-topology.md` หัวข้อ 5) แล้ว และทุกครั้งมันขุดเจอบั๊กหรือข้อความที่ไม่จริงในสเปก (ดู [[specs-must-say-who-owns-what]])

**ไฟล์ที่ต้องแก้พร้อมกันเสมอ 3 ตัว**: `ptl-batch-api-spec.md` (ต้นฉบับ) · `.apib` · `.html` — และตรวจ `.html` ด้วยเบราว์เซอร์จริงหลังแก้ (ดู [[prove-with-a-running-system]])
